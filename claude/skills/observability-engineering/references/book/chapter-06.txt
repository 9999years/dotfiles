                A Note from Charity, Liz, George, and Austin
In the last chapter, we broke down how metrics, logs, and traces can all be decom‐
posed into one common datatype: the arbitrarily wide, structured event—which can
be used to generate any view necessary during observability-based investigations.
However, we mostly focused on showing examples that illustrate the “structured
event” part of that datatype. In this chapter, we show you how to make those struc‐
tured events “arbitrarily wide.”
In observability, your structured events should be as wide as possible in order to
capture comprehensive context for debugging. Having rich context about any given
system event enables you to answer unexpected questions and perform complex
analysis without prejoining data. Some of the most useful data when investigating
novel or complex failures will typically involve comparing outliers across fields with
high cardinality.
Wide, structured events collapse the boundaries between logs, metrics, and traces
into a single data structure, offering a unified view for analyzing system behavior.
That means proactively designing your events so wide that they include fields to help
pinpoint issues such as user ID, feature flags, and request details in a single data
structure, eliminating the need for expensive and complex joins.
An “arbitrarily wide” structured event means that there should be no practical limit
to how much context can be stuffed into any single event. In a unified observability
system, you should have as much data available in your events to aid your investiga‐
tion as you think you might someday need. In practice, that means that any given
arbitrarily wide, structured event contains data that has both high dimensionality and
high cardinality.

In order to answer any arbitrary question, you’ll need to capture information about
a wide variety of conditions present in your systems. In the previous chapter, we
introduced simple examples structured around web server requests. Since our goal
was to show how telemetry datatypes are interrelated, we glossed over what all the
other useful attributes to capture would be.
You’ll capture data about system state when the request occurred by writing it to
various attributes. When considering what to capture, it’s relatively simple to come
up with a dozen or so attributes. But there are likely far more of these than you
would expect. In a well-instrumented codebase, there will typically be hundreds of
attributes.
In this chapter, I’ll walk you through that wide variety of system conditions and
concretely illustrate the types of values you should capture in each case. Note that
while this section contains a long list of attributes, it is definitely not exhaustive.

Service and Code Context
As you consider which attributes to capture, service and code context are good places
to start. These attributes are what turn questions like “Is something broken?” into
answers like “We know exactly which thing is broken, where, who’s responsible for it,
and what changed.”

Feature Flags
Fine-grained feature flags are a developer superpower. They enable you to test code
changes in production with only a fraction of your users or traffic. Coupled with the
broad visibility of wide events (as we’ll continue to see), the attributes in Table 6-6
can make even tricky migrations vastly more manageable and enable you to ship code
with confidence.

Table 6-6. Feature flag attributes
Attribute                             Examples Description
feature_flag.auth_v2                  true     Value of a particular feature flag for this request
                                      false
feature_flag.double_write_to_new_db true          Value of a particular feature flag for this request
                                    false


Adding these feature flag attributes would let you query an answer to “What errors
are the users in the new authentication flows hitting?” and “How does it compare to
the control group?”:
    SELECT
      COUNT
    WHERE
      main = true AND
      service.name = "api-service" AND
    GROUP BY feature_flag.auth_v2, exception.slug
Adding the flag information per request enables you to compare how the new code is
working as you opt more of your traffic into the new code path.

Request and Execution Flow
Telemetry about request and execution flow is what turns a single trace or log line
into a coherent narrative of how work moved through the system: what was called,
in what order, how long each step took, and where it failed. It’s the fastest way to go
from “the service is slow” to “this route is slow because this downstream call is slow.”
Focusing on these attributes is how you make finding answers like that repeatable at
scale.

Timings
In the work that gets done to respond to a request, I find it super useful to break it
up into a handful of important chunks and track how long each segment took on the
wide event.
You might be asking yourself, “Wait, isn’t that what child spans are for?”
Wrapping absolutely everything in its own span is the most common failure mode I
see when engineers first get access to tracing tools. You have to design the structure of
your data for the way you want to query it.
Child spans are helpful for waterfall visualization for a single request, but can be
difficult to query and visualize across all of your requests. Putting important timing
information on a single span makes it easier to query and also helps with tools like
Honeycomb’s BubbleUp (see Chapter 8), which can then immediately tell you that
a particular group of requests was slow because authentication took 10 seconds for
some reason.
An example of timing information to capture is shown in Table 6-12.

Table 6-12. Timing attributes
Attribute                       Examples Description
auth.duration_ms                52.2     How long we spent performing authentication during this request
                                0.2

Let’s say in your system you’ve just shipped a new subsystem that prioritizes payload
parsing for enterprise users, and you want to see the impact of that change on tail
latencies across all of the regions where you have systems deployed. If all of those
attributes are present on the wide event, then this is straightforward:
    SELECT
      P99(payload_parse.duration_ms)
    WHERE
      main = true AND
      service.name = "api-service"
    GROUP BY
      user.type,
      cloud.region

However, this may seem like we are duplicating data available in the child spans.
Surely we can accomplish the same thing by wrapping the payload parsing method in
its own span?
This is a valid approach, but now if we want to query that data alongside any
other data that we’ve captured in our wide event, querying has become much more
complicated, forcing the use of JOIN:
     SELECT
       P99(parse_span.duration_ms)
     FROM spans AS main_span
     JOIN spans AS parse_span ON main_span.trace_id = parse_span.trace_id
     WHERE
       main_span.main = true AND
       main_span.service.name = "api-service" AND
       parse_span.name = "payload-parse"
     GROUP BY main_span.user.type, main_span.cloud.region
Mature observability tooling is capable of running these types of queries at the cost
of additional processing; however, we should keep in mind how we will be using this
data. We want to prioritize quick, iterative exploration, often while responding to
active incidents, and we want any engineer on our team to be able to easily navigate
our observability tooling.
Viewed through this lens, identifying a few important timings and adding them to the
wide event is well worth the slight data duplication.

Errors
If you encounter an error and need to fail the operation, add attributes to the span
that contain the error information: type, stack trace, etc.
One approach that I have found incredibly valuable is tagging each location, where
we throw an error with a unique slug describing the error. If this string is unique
within your codebase, it’s easily found with a quick search. This enables you to jump

                                                                       Request and Execution Flow        |   99
straight from a spike in errors on a dashboard to the exact line of code throwing the
error. It also provides a convenient low-cardinality field to GROUP BY.
You’re unlikely to be able to wrap all possible errors, but any time a failed request
doesn’t have an exception.slug, that is a good sign that you have places in your code
where your error handling could be improved. It’s now really easy to find examples of
requests that failed in ways you didn’t anticipate.
You could add error handling into your instrumentation code like so:
      if isNotRecoverable(err) {
        // note the use of a plain string, not a variable
        // not dynamically generated
        // consider enforcing this with custom lint rules
        setErrorAttributes(err, "err-stripe-call-failed-exhausted-retries");
        throw err;
      }

there. Review what your instrumentation captures automatically, identify the gaps,
and fill them in. The difference between “something is slow” and “the /checkout
route is slow because authentication is taking 10 seconds for requests from mobile
clients on version 3.2.8” is often just a handful of well-chosen attributes that you
added yourself.

User and Business Context
Telemetry about user and business context is what lets you connect technical behav‐
ior to real-world impact: who was affected, what they were trying to do, and whether
the issue maps to a specific tenant, segment, plan, workflow, etc. It turns debugging
into prioritization because you can distinguish a “weird edge case” from a “revenue-
critical path breaking for high-value customers.”

User and Customer Information
Once you get the basics down, this is the most important piece of metadata that you
can add. No automagic SDK will be able to automatically understand the particular
details of your user model.

a month.
Be sure you can separate their traffic from others, by adding user attributes to your
wide events!

  • Memory leaks that only start to show up when the service has been running for a

A Convention to Filter Out Everything Else
While we are carefully crafting certain events to be “wide,” these are almost certainly
not the only events we’re emitting. You can still use other logs where it’s helpful!
I like to have a convention for identifying and searching for these “wide, structured
events.” I’ve landed on calling them “main” events. An example of how to tag these
with an attribute is shown in Table 6-21.

Table 6-21. A filtering attribute
Attribute Examples Description
main      true     Present only for spans designated as a “wide event,” usually wrapping a request or response, or a
                   background job

I find this helpful when approaching new systems. I can quickly get a view of what
work a system does and an idea of how the traffic for that system is distributed by
asking for all of the main spans and grouping by the span name:
      SELECT
        COUNT(*)
      WHERE
        main = true AND
        service.name = "other-teams-service"
      GROUP BY name
It’s also helpful for eliminating noise. If I’d like to calculate the error rate of requests
into the system, I might query based on the HTTP status code:
      SELECT
        SUM(IF(http.response.status_code >= 500, 1, 0)) / COUNT(*) AS error_rate
      WHERE
        main = true AND
        service.name = "api-service"


However http.response.status_code is also present on child spans for any outgo‐
ing subrequest. Without the main = true filter, we’ll get an incorrect error rate
calculation here.
